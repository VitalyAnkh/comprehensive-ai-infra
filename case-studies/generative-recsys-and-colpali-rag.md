## 生成式推荐在线打分千级候选物品的前缀共享边界

当工业界把推荐精排从碎片化浅层交叉网络切换为类似语言模型的层次化序列转导器（如 `16` 层、`d = 1,024` 的 `HSTU` 主干）时，直接套用对话推理方式会立即碰壁：对话每步只需对词表解码 1 个位置，而推荐精排必须在 `< 15 ms` 内对同一用户历史序列（$L_{\mathrm{hist}} = 4{,}096$）下的 $M = 1{,}024$ 个召回候选物品逐一输出多目标概率。独立拼接执行 `1,024` 次前向需要 $1{,}024 \times 1.37627 \approx \mathbf{1{,}409.3\ \mathrm{TFLOPs}}$，超过单张 H100 在数十毫秒窗口内的物理算力上限。

`M-FALCON` 的核心机制与第 8 章前缀缓存一脉相承，但针对候选互不可见约束做了两段式分块特化：
1. **单次历史前缀编码**：对 $L_{\mathrm{hist}} = 4{,}096$ 的交互前缀仅算 1 次（`1.376 TFLOPs`），将键值状态固定在片上缓存；
2. **块对角跳过候选微批**：将 `1,024` 个候选排成紧凑矩阵，在左半区复用全部 `4,096` 列历史状态跑稠密 `WGMMA` 矩阵乘，在右半区跳过全部 $1{,}024 \times 1{,}023$ 个非对角无效块、仅在寄存器内追加对角线自内积。候选阶段计算量固定在 `30.084 TFLOPs`，单请求总工作量降至 **`31.46 TFLOPs`**（压缩 **`44.80 倍`**），使 32 张 H100 精排实例组（4 台 8 卡 HGX H100，单卡持续算力 `476.8 TFLOPS`、`MFU 48.2%`，全组有效持续算力 `15,258.1 TFLOPS`）可稳定提供 **`485 QPS`**（单卡约 `15.2 QPS`，每秒打分 `496,640` 个物品，`P99 = 11.8 ms`）。

## 视觉文档晚交互检索的容量膨胀与残差量化账本

在企业复杂 PDF 知识库（含跨栏财报表格、电路框图与扫描公式）中，传统 `OCR -> 切块 -> 单一稠密向量` 管线容易因版面解析失真而召回大量无关片段，迫使下游生成模型（如 [Qwen3-8B](../calculations/configs/models/qwen3-8b/config.json)，每词元 `144 KiB` KV 状态，或 `DeepSeek-V3` MLA 模型）为几十篇噪声文档付出数倍预填充算力（见[检索与生成的协同预算](retrieval-and-generation.md)）。

`ColPali` 绕过 OCR，直接把每页文档图像编码为 $N_p = 1{,}030$ 个 $d = 128$ 维视觉词元，通过晚交互算子 $S(q, P) = \sum_{i=1}^{N_q} \max_{j=1}^{N_p} \langle q_i, p_j \rangle$ 对齐局部图文，将复杂图表页检索 `nDCG@5` 从 `0.542` 提升至 **`0.816`**。但其原始存储代价随词元数线性放大：

$$B_{\mathrm{page}}^{\mathrm{BF16}} = 1{,}030 \times 128 \times 2\ \mathrm{B} = 263{,}680\ \mathrm{B} = \mathbf{263.68\ \mathrm{KB/page}}$$

对于 `5,000 万`页（$5 \times 10^7$）文档库，朴素 `BF16` 体积达 **`13.18 TB`**（`1 亿`页达 **`26.37 TB`**，`10 亿`页达 **`263.7 TB`**）。工程落地必须采用 **`PLAID` 聚类中心索引 + 低比特残差量化**：
- **`PLAID 2-bit` 方案**：每个视觉词元记录 `2 B`（`uint16`）精细聚类中心编号与 $128 \times 2 / 8 = 32\ \mathrm{B}$ 的 `2-bit` 量化残差，合 **`34.0 B/vec`**（压缩 **`7.53 倍`**），`5,000 万`页降至 **`1.75 TB`**；
- **`PLAID 1-bit` 方案**：采用子簇局部 `12-bit` 紧凑中心编号（`1.5 B/vec`）加 `16 B` 二值符号残差，合 **`17.5 B/vec`**（压缩 **`14.6 倍`**），`5,000 万`页仅需 **`901.3 GB`**（精确值 `901.25 GB`；`1 亿`页 **`1.80 TB`**，`10 亿`页 **`18.0 TB`**）。

在线查询通过“倒排质心表剪枝 -> 质心近似打分 -> Tensor Core 融合位解压与 `MaxSim` 精排”三级执行，无需在全局显存展开 `BF16` 张量即可在 **`14.2 ms`**（`P99`）内完成检索。而在通用混合文本与多模态检索管线中，采用 `BM25 Block-Max WAND`（`6.4 ms`）与 `cuVS CAGRA`（`9.8 ms`）并行召回 $K_1 = 1{,}000$，经 `0.8 ms` 倒数秩去重后仅送 $K_2 = 64$ 个高潜候选进入紧凑装箱的 `0.6B` 交叉编码器（`14.6 ms`），计入 `2.4 ms` 网关开销后端到端 `P99` 为 **`27.6 ms < 30.0 ms`**。

## 流式特征频次准入与无锁 Epoch 双缓冲热更新

搜广推在线模型效果高度依赖分钟级乃至秒级的新鲜行为反馈，但实时流式入库同时带来容量膨胀与读写锁竞争两大工程风险：

1. **布谷鸟频次准入过滤（$\tau = 5$）**：在日新增 `40 亿`次曝光点击流下，大量交叉组合 ID 属于仅偶然出现 1～2 次的长尾噪声。若无准入拦截，30 天累积原始稀疏表体积达 `2.40 TB`（`2,400.0 GB`）。前置轻量级布谷鸟频次过滤器要求新特征累计出现达 $\tau = 5$ 次方可分配真实嵌入槽位（幂律准入比例 `36.5%`），再配合 30 天不活跃指数衰减淘汰（留存系数 `0.8630`），常驻活跃嵌入表缩减 **`68.5%`** 至 **`756.0 GB`**，从源头防止一次性噪声污染 HBM 热层；
2. **RCU / Epoch 无锁原子切换**：当后台 `Flink` 流式训练每秒向线上推送 `250 万`个增量更新向量（跨 `4,096` 个哈希分段）时，若采用原地分段读写锁，单次在线请求并发扇出查询 `320` 个特征槽位时遭遇写锁排斥与线程护航的概率会叠加放大，导致在线查表 `P99` 尾延迟从 `1.08 ms` 恶化至 **`18.4 ms`**。改用基于代际回收（`Epoch-Based Reclamation, EBR`）的双槽无锁发布后，写线程在影子槽位写完新向量再原子翻转指针，读线程仅递增代际计数、全程零阻塞读取，在线查表 `P99` 稳定在 **`1.15 ms`**（尾延迟降低 **`16.0 倍`**），而 `3-Epoch` 延迟回收队列与影子缓冲区的总额外内存开销仅为 **`+6.2%`**。
